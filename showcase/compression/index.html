    How ZIP Makes Files Smaller: Huffman Coding

    A text file spends exactly 8 bits on every character, whether it's the letter you type constantly or one you almost never use. That's wasteful, and fixing the waste without ever losing a single bit of the original is the problem this lesson solves.

    This part: why fixed-length bytes waste space → Morse code's idea → why variable-length codes can be ambiguous → prefix-free codes as paths in a tree → the quantity we minimise, $\sum p_i \ell_i$ → Huffman's algorithm, built on your own text → why the greedy choice is optimal → entropy, the floor no code can beat → how ZIP's DEFLATE combines Huffman with LZ77 → why random data won't compress.
    Next part: beating Huffman's 1-bit limit with arithmetic coding, and modelling context.
    Assumed: you know what a bit and a byte are, and you're comfortable with logarithms. Everything else is built here.

    1The problem: every character costs 8 bits

    Save the text mississippi river to a file and you get 17 bytes. Each character, including the space, is stored as one byte: in ASCII (and in UTF-8, which agrees with ASCII for these characters) m is 01101101, i is 01101001, and so on. That's $17 \times 8 = 136$ bits.

    Look at what those 136 bits are spent on. The letter i appears 5 times and v once, yet both cost exactly 8 bits. Worse, a byte can distinguish 256 different characters, but this text only uses 8 of them. We're paying for a menu of 256 items and ordering from 8.

    Type anything into the box below and look at the shape of the counts. Every widget in this lesson that has a text box shares it, so whatever you type here follows you through the page.

    There are two separate kinds of waste here, and it's worth keeping them apart because they're fixed by different ideas.

    The first is alphabet waste. With only 8 distinct symbols, 3 bits per symbol are enough to give each its own pattern ($2^3 = 8$): say 000 for i, 001 for s, and so on. That brings 136 bits down to $17 \times 3 = 51$, provided the reader knows the 8-entry table. Useful, but it treats i and v the same.

    The second is frequency waste: i is five times as common as v, and a fixed-length code ignores that. In typical English, the letter e is roughly one letter in eight while z is fewer than one in a thousand. So here is the question for the rest of the lesson: can we spend fewer bits on common symbols and more on rare ones, and come out ahead on average, while still being able to recover the original exactly? "Exactly" matters. This is lossless compression: a ZIP file must give back every byte, unlike a JPEG, which may throw detail away.

    2The insight from Morse code

    People had this idea long before computers. Telegraph operators sending Morse code tapped every symbol by hand, so time was the cost, and the code was arranged so that the most common letters were the cheapest to send:

    letterMorsetaps
    E·1
    T−1
    A·−2
    N−·2
    Q−−·−4
    Z−−··4

    E, the most common letter in English, is a single dot. Q and Z, which are rare, take four symbols. If you send mostly E's and T's, your average message gets short. That's the whole idea of variable-length coding: give frequent symbols short codes and rare symbols long ones.

    But Morse hides a cheat. Between letters, the operator leaves a pause, and between words a longer one. The pause is effectively a third symbol, which tells the listener "this letter is finished." A computer file has only 0s and 1s, with no pause. So let's do what a computer would have to do: map dot to 0, dash to 1, and drop the pauses.

    3Variable-length codes can be ambiguous

    Take just those four letters with their Morse patterns as bits: $e = \texttt{0}$, $t = \texttt{1}$, $a = \texttt{01}$, $n = \texttt{10}$. Now someone sends you 0110. What was the message?

    What exactly went wrong? Look at the first two bits, 01. The decoder has seen 0, which is a complete codeword (e), but it's also the start of another codeword (a is 01). It can't know whether to stop. The same clash happens between t = 1 and n = 10. The trouble is always the same shape: one codeword is a prefix (a beginning) of another.

    So remove that possibility. Require that no codeword is the beginning of any other one. The second code in the widget, $e = \texttt{0}$, $t = \texttt{10}$, $a = \texttt{110}$, $n = \texttt{111}$, obeys this rule. Read 0110 with it: 0 is e, and nothing else starts with 0, so the decoder commits immediately; then 1 isn't a codeword, 11 isn't either, 110 is a. One reading, "ea", found without ever looking ahead.

    Definition · prefix-free code

    A code assigns each symbol a string of bits, its codeword. The code is prefix-free (often just called a prefix code) if no codeword is a prefix of another codeword. The length of symbol $i$'s codeword is written $\ell_i$.

    Careful · the name is backwards

    "Prefix code" means a code that is free of prefixes, not one built from them. Also, prefix-free is a sufficient condition for decodability, not a necessary one: some codes are uniquely decodable while violating it, but they make the decoder wait and look ahead. It's known (the Kraft–McMillan theorem) that such codes can never achieve shorter lengths than the best prefix-free code, so nothing is lost by insisting on prefix-free, and decoding stays instantaneous.

    4Prefix-free codes are paths in a binary tree

    There's a picture that makes the prefix condition obvious. Start at a root and read a codeword bit by bit: 0 means "go left", 1 means "go right". Every codeword becomes a path, and the symbol sits wherever its path ends. The codeword's length $\ell_i$ is the symbol's depth in the tree.

    Now ask what "one codeword is a prefix of another" means in the picture. If 0 is a prefix of 01, then the path to a passes through the node where e sits. That's the red ring in the Morse-like tree above: a symbol sitting on the way to another symbol. So the prefix condition has a clean geometric meaning: a code is prefix-free exactly when every symbol is at a leaf, a node with nothing below it.

    And this is why decoding is instantaneous. Start at the root, follow one edge per bit, and the moment you land on a leaf, you've finished a symbol, because there is nowhere further to go. Output it and jump back to the root. Watch it happen:

    The price of a short codeword

    The tree also shows the catch. Giving e the 1-bit codeword 0 uses up the entire left half of the tree: nothing else may start with 0, so every other symbol is pushed into the right half and gets longer. Short codewords are expensive. How expensive, exactly?

    Imagine all bit strings of some long length $D$ (at least as long as every codeword). There are $2^D$ of them. A codeword of length $\ell$ "claims" every one of those strings that begins with it, and there are $2^{D-\ell}$ such strings. Because no codeword is a prefix of another, no long string begins with two different codewords, so the claimed sets never overlap:

    $$\sum_i 2^{D-\ell_i} \le 2^D$$
    the claimed sets are disjoint, so together they can't exceed all $2^D$ strings
    $$\sum_i 2^{-\ell_i} \le 1$$
    divide both sides by $2^D$
    $$\tfrac12 + \tfrac14 + \tfrac18 + \tfrac18 = 1$$
    check: our code $e, t, a, n$ with lengths 1, 2, 3, 3 spends the budget exactly

    This is the Kraft inequality. Read $2^{-\ell}$ as the share of a budget of 1 that a codeword of length $\ell$ consumes: a 1-bit codeword costs half the budget, a 2-bit codeword a quarter, and so on. It works in the other direction too: any lengths that fit the budget can be realised by some prefix-free code (assign codewords shortest first, each time taking the leftmost free node at the right depth). So designing a code really means choosing lengths that fit the budget. The question is which lengths.

    5What we're optimising: expected bits per symbol

    Suppose symbol $i$ makes up a fraction $p_i$ of the text: in mississippi river, $p_{\texttt{i}} = 5/17$. If it gets a codeword of length $\ell_i$, then a text of $n$ characters costs $\sum_i (n\,p_i)\,\ell_i$ bits, since symbol $i$ appears $n p_i$ times and each appearance costs $\ell_i$ bits. Dividing by $n$ gives the number that matters.

    Definition · expected code length

    $$\bar L = \sum_i p_i\,\ell_i \quad \text{bits per symbol},$$ where $p_i$ is the probability (here, the relative frequency) of symbol $i$, and $\ell_i$ is the length of its codeword. Each symbol's length is weighted by how often you pay it. Total size is $n \bar L$ bits.

    Notice why this form and not another. We don't minimise the longest codeword, or the plain average of the lengths: a 9-bit codeword for a symbol that appears once is nearly free, while one extra bit on i costs 5 bits in our text. The weights $p_i$ say where bits are worth saving.

    So the whole problem fits in one line: choose whole-number lengths $\ell_i$ that minimise $\sum_i p_i \ell_i$, subject to the budget $\sum_i 2^{-\ell_i} \le 1$. The two pull against each other. Shortening the code of i lowers the sum but eats budget, forcing other codes longer.

    Worked example · the fixed 3-bit code

    For mississippi river the counts are i 5, s 4, p 2, r 2, and 1 each for m, v, e and the space: 8 symbols, 17 characters. With 3 bits for everything, $\bar L = \sum_i p_i \cdot 3 = 3 \sum_i p_i = 3$ bits per symbol, or 51 bits total. Its budget: $8 \times 2^{-3} = 1$, fully spent. Can a better split of the same budget, short codes for i and s and long ones for the singletons, do better? Let's find the best one.

    6Huffman's algorithm: merge the two rarest

    In 1951, David Huffman was a graduate student in Robert Fano's information theory course at MIT, and he solved exactly this problem; the method was published in 1952 as "A Method for the Construction of Minimum-Redundancy Codes." Fano and Claude Shannon had a top-down method that split the symbols into two groups of roughly equal probability, but it isn't always optimal. Huffman's trick was to build the tree from the bottom up.

    Think about where the rarest symbols should go. Some symbols must sit at the deepest level of the tree; it's cheapest if they're the ones you rarely pay for. And in a good tree, a deepest leaf always has a sibling (if it didn't, you could delete its last bit and lose nothing). So the two rarest symbols can be placed side by side at the very bottom, as siblings that differ only in their final bit.

    Here's the step that makes the algorithm work. Once two symbols are glued together as siblings, the rest of the tree only ever sees their parent. To the rest of the tree, "v or e" behaves like one combined symbol whose weight is the sum of both. So replace the pair with that combined symbol, and you have the same problem with one fewer symbol. Repeat until one tree remains.

    Algorithm · Huffman coding

    1. Make one single-node tree per symbol, weighted by its count (or probability).
    2. Take the two trees with the smallest weights. Make them the left (0) and right (1) children of a new node whose weight is their sum.
    3. Repeat step 2 until a single tree remains. Each symbol's codeword is its path from the root.
    With $k$ symbols there are exactly $k - 1$ merges. Ties can be broken any way you like: different choices give different codes with the same $\bar L$.

    Let's run it on mississippi river by hand. Ties are broken by taking older trees first, which is what the widget does:

    mergelightest two treesnew weight
    1␣ (1) + e (1)2
    2m (1) + v (1)2
    3p (2) + r (2)4
    4{␣,e} (2) + {m,v} (2)4
    5s (4) + {p,r} (4)8
    6{␣,e,m,v} (4) + i (5)9
    7{s,p,r} (8) + {␣,e,m,v,i} (9)17

    The result gives i and s 2-bit codes, p and r 3-bit codes, and the four singletons 4-bit codes. Check the budget: $2 \cdot \tfrac14 + 2 \cdot \tfrac18 + 4 \cdot \tfrac1{16} = 1$. Spent exactly, as it always is for a Huffman tree, because every internal node has two children.

    Now the cost. There's a lovely shortcut hiding in the widget's last message. Each merge adds one bit to every occurrence of every symbol under the new node, so it adds exactly the new node's weight to the total. The total is therefore just the sum of all merge weights:

    $$\text{bits} = \sum_i \text{count}_i \cdot \ell_i$$
    every occurrence of symbol $i$ costs $\ell_i$ bits
    $$= 5\cdot2 + 4\cdot2 + 2\cdot3 + 2\cdot3 + 4\cdot(1\cdot4)$$
    i and s at depth 2; p and r at depth 3; m, v, e, ␣ at depth 4
    $$= 10 + 8 + 6 + 6 + 16 = 46$$
    add up the cost of each symbol
    $$= 2 + 2 + 4 + 4 + 8 + 9 + 17 = 46$$
    same total from the merge weights: each merge adds one bit to everything beneath it
    $$\bar L = \tfrac{46}{17} \approx 2.706 \text{ bits/symbol}$$
    divide by the 17 characters

    46 bits, against 51 for the fixed 3-bit code and 136 for plain bytes. Most of the drop from 136 is alphabet waste (136 → 51); Huffman's use of the frequencies takes the next 5 bits (51 → 46), about 10%. On real English text, with a steeper frequency curve, the second effect is larger.

    Careful · the decoder needs the code too

    The 46 bits are useless without the code table. For a 17-character message, describing the table costs on the order of the 90 bits we saved, so this tiny file wouldn't actually shrink. On a file of thousands of characters the table is a small fixed cost. DEFLATE makes it smaller still by sending only each symbol's code length, from which the decoder rebuilds an agreed "canonical" code (§9).

    7Why the greedy choice is optimal

    Merging the two rarest looks like a reasonable heuristic, the kind that usually works. In fact it is always optimal: no prefix-free code for these frequencies has a smaller $\bar L$. The argument is short and worth owning, because it tells you why the algorithm is shaped the way it is. It has three parts.

    First, an optimal tree has no wasted branches. If some internal node had only one child, you could delete that node and pull its subtree up one level: every code below it gets one bit shorter and the code stays prefix-free. So in an optimal tree every internal node has two children, which means the deepest leaf has a sibling leaf at the same depth.

    Second, rare symbols can always go deepest. This is an exchange argument. Suppose a common symbol $a$ sits deeper than a rarer symbol $x$: $p_a \ge p_x$ but $d_a > d_x$. Try swapping them and see what happens to the cost.

    $$\text{before: } p_a d_a + p_x d_x \qquad \text{after: } p_a d_x + p_x d_a$$
    swap which symbol sits at which leaf; nothing else changes
    $$\text{after} - \text{before} = p_a(d_x - d_a) + p_x(d_a - d_x)$$
    subtract and group the terms by symbol
    $$= (p_a - p_x)(d_x - d_a) \le 0$$
    first factor $\ge 0$ (a is more common), second $< 0$ (x was shallower): the swap never hurts

    Keep swapping and the two rarest symbols end up in the two deepest positions, which by the first point can be a pair of siblings, without the cost ever going up. So some optimal tree has the two rarest symbols as deepest siblings. That's precisely what Huffman's first merge commits to. Try the exchange yourself on the tree shape Huffman found:

    Third, merging reduces the problem honestly. Take a tree $T$ in which the rarest two, $x$ and $y$, are siblings, and let $T'$ be the same tree with $x$ and $y$ replaced by a single leaf $z$ of weight $p_x + p_y$, one level up. Their codes in $T$ are one bit longer than $z$'s code in $T'$, so

    $$\bar L(T) = \bar L(T') + p_x + p_y.$$

    The extra term $p_x + p_y$ is the same whatever $T'$ looks like. So the best $T$ comes from the best $T'$: the problem with one fewer symbol, which is exactly what the algorithm solves next. By induction on the number of symbols (a single symbol is trivially optimal), every Huffman tree is optimal. Notice that this equation is the "add the merge weight" shortcut from §6, now doing the work of a proof.

    Key idea

    Huffman never has to look ahead. The two rarest symbols belong together at the bottom of some optimal tree, and after merging them the remaining problem is the same problem, smaller. Greedy choices that keep the remaining problem the same shape are what make greedy algorithms correct.

    8The floor: entropy

    Huffman finds the best prefix-free code. But how good is "best"? Is there a number, depending only on the frequencies, that says how far any such code could ever go? There is, and the budget from §4 leads straight to it.

    Suppose every probability were a power of ½, as with $p = (\tfrac12, \tfrac14, \tfrac18, \tfrac18)$. Then choose $\ell_i = \log_2(1/p_i)$, giving lengths 1, 2, 3, 3. The budget is $\sum 2^{-\ell_i} = \sum p_i = 1$: exactly spent. Each symbol gets a share of the budget equal to its share of the text, which is about as fair as an allocation gets. That's our $e, t, a, n$ code, and its average length is $\sum p_i \log_2(1/p_i) = \tfrac12 \cdot 1 + \tfrac14 \cdot 2 + \tfrac18\cdot 3 + \tfrac18 \cdot 3 = 1.75$ bits. This quantity has a name.

    Definition · entropy (Shannon, 1948)

    $$H = -\sum_i p_i \log_2 p_i = \sum_i p_i \log_2 \frac{1}{p_i} \quad \text{bits per symbol}.$$ Read $\log_2(1/p_i)$ as the ideal length for a symbol of probability $p_i$: a symbol that appears half the time deserves 1 bit, one that appears a sixteenth of the time deserves 4. $H$ averages those ideal lengths with the same weights $p_i$ as $\bar L$. Symbols with $p_i = 0$ contribute nothing.

    Two facts make $H$ the right yardstick. They're the core of Shannon's source coding theorem, applied to codes that encode one symbol at a time.

    No prefix-free code beats it: $\bar L \ge H$ for every code that fits the budget. The proof is three lines, using one inequality: since $\log_2$ is concave, the average of $\log_2$ of some numbers is at most $\log_2$ of their average (Jensen's inequality).

    $$H - \bar L = \sum_i p_i \log_2 \frac1{p_i} - \sum_i p_i \log_2 2^{\ell_i} = \sum_i p_i \log_2 \frac{2^{-\ell_i}}{p_i}$$
    write $\ell_i$ as $\log_2 2^{\ell_i}$ and combine the logs
    $$\le \log_2 \sum_i p_i \cdot \frac{2^{-\ell_i}}{p_i} = \log_2 \sum_i 2^{-\ell_i}$$
    Jensen: a $p$-weighted average of logs is at most the log of the $p$-weighted average
    $$\le \log_2 1 = 0$$
    the Kraft budget: $\sum_i 2^{-\ell_i} \le 1$

    And Huffman comes within 1 bit of it: $H \le \bar L_{\text{Huffman}} < H + 1$. The ideal lengths $\log_2(1/p_i)$ usually aren't whole numbers. Round each one up, $\ell_i = \lceil \log_2(1/p_i) \rceil$: rounding up only shrinks each $2^{-\ell_i}$, so these lengths still fit the budget, and each is less than one bit above its ideal, so their average is below $H + 1$. Huffman is optimal, so it does at least as well as this rounded-up code.

    9What ZIP actually does: DEFLATE

    Huffman alone looks at symbols one at a time, as if each character were drawn independently from the same frequency table. Real files aren't like that. Source code repeats identifiers, HTML repeats tags, logs repeat whole lines. To Huffman, abababab is just "half a's, half b's": 1 bit per symbol, 8 bits. Yet the whole string could be described as "ab, then repeat it 3 more times." Huffman can't see repetition or context, because it only sees counts.

    DEFLATE, the format inside ZIP files, gzip and PNG images, handles this with a second component that runs before Huffman. It was designed by Phil Katz for PKZIP and is specified in RFC 1951 (1996). The first stage is LZ77, named after Abraham Lempel and Jacob Ziv's 1977 paper: whenever the text repeats something seen recently, replace the repeat with a back-reference, "go back $d$ characters and copy $\ell$ of them." In DEFLATE, $d$ can reach back up to 32,768 bytes and $\ell$ runs from 3 to 258.

    Then Huffman finishes the job on the tokens. DEFLATE uses two Huffman codes per block. One covers an alphabet of 286 symbols: the 256 possible byte values as literals, an end-of-block marker, and 29 symbols for match lengths (with a few extra raw bits to pick an exact length inside a range). The other covers 30 symbols for distances, again with extra bits. Short, common distances and common lengths get short codes, just like i did.

    Two practical details connect back to what we built. Each block can carry its own dynamic Huffman codes, described compactly by listing only each symbol's code length (a "canonical" code, which the decoder reconstructs from the lengths alone; the lengths themselves are Huffman-coded too), or use a fixed code defined in the standard, or be stored uncompressed. And DEFLATE caps code lengths at 15 bits, so when Huffman's tree is deeper than that, an encoder has to adjust the lengths, giving up a little optimality for a bounded decoder.

    Key idea

    LZ77 removes repetition (long-range structure); Huffman removes skewed frequencies (symbol-level structure) in what's left. Neither does the other's job, which is why DEFLATE uses both.

    Huffman's two built-in limits still apply after LZ77. It treats each token as independent of the previous one, so it can't exploit context like "after q comes u". And every codeword is a whole number of bits, so very common symbols are overcharged, the gap you saw in the skew slider. Newer formats attack these limits: arithmetic coding and asymmetric numeral systems (ANS) can effectively spend fractions of a bit per symbol, and context models predict each symbol from what came before. That's Part 2.

    10Uniform and random data: nothing to squeeze

    Go back to the first widget and press 200 random letters, then look at the encoder. The bars are roughly flat, the entropy is close to $\log_2 26 \approx 4.70$ bits, and Huffman lands near it. The only saving over bytes comes from the alphabet: 26 letters need about 4.7 bits rather than 8, which is the alphabet waste from §1, not frequency waste. Now imagine truly random bytes, all 256 values equally likely. Then $H = \log_2 256 = 8$ bits, every Huffman code is 8 bits long, and there is nothing at all to gain. The skew slider at 0 shows the same thing in miniature: uniform in, no saving out.

    This isn't a weakness of Huffman; no lossless compressor can shrink every input. Here's the counting argument, and it needs nothing but arithmetic:

    $$\#\{\text{files of exactly } n \text{ bits}\} = 2^n$$
    each of the $n$ bits is 0 or 1
    $$\#\{\text{files shorter than } n \text{ bits}\} = 2^0 + 2^1 + \cdots + 2^{n-1} = 2^n - 1$$
    add up all shorter lengths (a geometric series)
    $$2^n - 1 < 2^n$$
    so if every $n$-bit file shrank, two would share an output, and decompression couldn't tell them apart

    A compressor is a bet that its inputs have structure: skewed frequencies, repetition, predictable context. When the bet loses, the best it can do is not grow the file much, which is why DEFLATE has a "stored" block type that just copies the bytes. It's also why zipping a JPEG, an MP4, or another ZIP saves almost nothing: their bytes have already been compressed, and look nearly random to Huffman.

    Careful · entropy depends on the model

    The $H$ in this lesson is computed from single-character frequencies, so it's the floor for codes that encode one character at a time with a fixed table. abababab has $H = 1$ bit per symbol under that model, yet it is perfectly predictable. A model that looks at the previous character would assign it far lower entropy. "Random-looking to Huffman" and "incompressible" are not the same thing.

    Show answer

    Counts: a 4, b 2, c 1. Merge c (1) and b (2) into weight 3, then that tree (3) with a (4) into 7. So a gets 1 bit and b, c get 2 bits: $4\cdot1 + 2\cdot2 + 1\cdot2 = 10$ bits, against 56 as bytes. Merge-weight shortcut: $3 + 7 = 10$. Entropy: $H = \tfrac47\log_2\tfrac74 + \tfrac27\log_2\tfrac72 + \tfrac17\log_2 7 \approx 1.379$ bits, so $7H \approx 9.65$ bits; Huffman's $10/7 \approx 1.429$ bits/symbol is within 1 bit of $H$, as promised.

    2. Spot the waste. Is the code $\{\texttt{0}, \texttt{10}, \texttt{110}, \texttt{1110}\}$ prefix-free? Could it be improved without looking at any frequencies?

    Show answer

    It is prefix-free: every codeword ends at a leaf. But its Kraft sum is $\tfrac12 + \tfrac14 + \tfrac18 + \tfrac1{16} = \tfrac{15}{16} < 1$, so budget is left over. In the tree, node 111 has only one child, 1110. Replace 1110 by 111: still prefix-free, and that symbol is one bit cheaper whatever the frequencies. This is the "no wasted branches" step of the optimality proof.

    3. Predict. A file is the two characters ab repeated 10,000 times. Roughly what will Huffman alone achieve, and what will DEFLATE achieve? Why the difference?

    Show answer

    Huffman sees $p_a = p_b = \tfrac12$, so 1 bit per character: 20,000 bits, 8× smaller than bytes but nowhere near the structure's true simplicity. LZ77 emits two literals and then back-references with distance 2 (each copy at most 258 long, so roughly 78 of them), and Huffman codes those few tokens: a file of a few dozen bytes. The difference is that the information is in the order of symbols, which only LZ77 sees.

    4. Find the flaw. Someone claims their compressor makes every file at least one byte smaller, so running it repeatedly shrinks anything to nothing. Show it can't be lossless.

    Show answer

    There are $2^n$ files of $n$ bits but only $2^n - 1$ shorter files, so two different inputs would map to the same output, and the decompressor couldn't know which to return. Any lossless compressor that shrinks some files must grow others (or leave them the same size).

    5. Explain. In the skew widget at the far right, why does Huffman's curve level off near 1 while the entropy keeps falling toward 0?

    Show answer

    Every symbol needs a codeword of at least one bit, so $\bar L \ge \sum_i p_i \cdot 1 = 1$. Entropy has no such floor: a symbol with probability near 1 carries almost no information, $\log_2(1/p) \to 0$. The difference is the integer-length restriction, and removing it (coding many symbols jointly, or with arithmetic coding) is the subject of Part 2.

    Next, Part 2: past the 1-bit wall. Huffman's codewords are whole bits, so a symbol with probability 0.95 still costs a full bit. Arithmetic coding encodes a whole message as a single number in an interval that shrinks by a factor $p$ for each symbol, getting within a few bits of $nH$ for the entire message. Then we'll let the probabilities depend on context, which is where modern compressors get their power.
